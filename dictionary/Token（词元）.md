[模型](./模型（Model）.md)读取和写入的原子单位。大小约等于一个单词，但并不完全对应——常见词通常是一个 Token（词元），而罕见词或长词会被拆分成好几个。[上下文窗口](./上下文窗口（Context%20window）.md)大小、费用和延迟，全都是以 Token 来计数的。

文本通过分词器（tokenizer）变成 Token：这是一个在[训练](./训练（Training）.md)前就学习好的、包含数万个片段的固定词表，负责把任何输入切分成一串词表条目。模型从来看不到单个字符或完整单词——每段文本在进入时都会被转换成 Token，而[下一个 Token 预测](./下一个%20Token%20预测（Next-token%20prediction）.md)在输出时也是一个 Token 接一个 Token 地生成。

按经验法则，一个 Token 大约相当于四分之三个英文单词，所以一千个 Token 大约是 750 个英文词。代码的情况则没那么规律：常见的关键字和惯用写法会被紧凑地分词，而自动生成的标识符、哈希值、base64 数据块以及压缩混淆后的代码，则会把一个“词”拆成大量 Token。规律在于：在分词器原始语料中频繁出现的文本会获得简短高效的编码；没怎么出现过的文本则会被切碎成许多小块。像 `a3f9c2e1` 这样的哈希值从未在语料中出现过，因此会被拆成很多个 Token，而 `function` 只占一个。这就是为什么一个看起来不大的文件，如果里面充斥着冷门字符串，就会占用惊人比例的上下文窗口。

Token 是衡量其他一切指标的基本单位。费用按 Token 计算——提供商分别对[输入 Token](./输入%20Token（Input%20tokens）.md) 和[输出 Token](./输出%20Token（Output%20tokens）.md) 计价。速度以每秒 Token 数衡量，因为输出是一个 Token 接一个 Token 生成的。而上下文窗口是固定数量的 Token，所以你传入的文件总共有多少 Token，决定了里面还能装下多少内容。

_避免使用：_ “词（word）”——Token 的边界与单词边界并不一致，而且真正关键的度量单位是“每秒 Token 数”和“每美元 Token 数”。

_用法示例：_

“这个提示词大概会有多大？”

“先跑一下分词器看看——schema 本身很紧凑，但那些 JSON 键名很奇怪，拆出来的 Token 会比你想的要多。”
