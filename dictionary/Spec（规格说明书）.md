一种描述跨多[会话](./会话（Session）.md)工作的[交接产物](./交接产物（Handoff%20artifact）.md)——说明要构建什么，而不是每轮会话各自如何完成自己的那部分。它会随着工作推进不断更新，由多个 [Ticket](./Ticket（任务单）.md) 组成。

Spec 之所以存在，是因为会话是一次性的，而大型工作不是。任何需要超过一个[上下文窗口](./上下文窗口（Context%20window）.md)工作量的任务，都需要一个在[上下文](./上下文（Context）.md)之外安身的地方——位于 Agent 所处[环境](./环境（Environment）.md)中的某个位置，能够在[清空会话](./清空会话（Clearing）.md)后依然留存，无论是仓库里的文件、GitHub Issue，还是 Agent 可以访问的问题追踪系统。Spec 就是这样一个家：记录着目标、约束条件、迄今为止做出的决策，以及各个 Ticket 及其状态的列表。任何新会话只要读取它，就能了解当前进度，而无需继承上一个会话积累的噪声。

Spec 有几种常见的形式，大多沿用了团队日常的文档习惯。_产品需求文档（PRD）_ 偏重面向用户的“做什么”和“为什么”——功能、行为、验收标准。_设计文档_或 _RFC_ 偏重技术——选定的方案、被否决的替代方案以及权衡考量。在规模较小的一端，一份附带 Ticket 检查清单的普通 `plan.md`，也能在跨多会话的功能开发中起到同样作用。形式本身不如它的角色重要：对 [Agent](./Agent（智能体）.md) 而言，这些都是同一回事——在每次会话开始时读取的持久化意图声明。

_用法示例：_

“这些要全放在一个会话里做完吗？”

“不，把它写成一份 Spec——拆分成多个 Ticket，每个 Ticket 在独立的会话里跑。试图在单个上下文里做完所有事，还没到一半就会掉进[愚钝区](./聪明区（Smart%20zone）.md)。”
