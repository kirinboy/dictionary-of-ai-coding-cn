一种工作体系：由触发器——比如新建 Issue、定时任务、CI 失败、另一个会话结束——来启动 [Agent](./Agent（智能体）.md) [会话](./会话（Session）.md)，而不是由人类手动开启，从而让更多工作以[无人值守（AFK）](./无人值守（AFK）.md)模式运行，把宝贵的人类注意力留给那些真正需要[人在回路（HITL）](./人在回路（Human-in-the-loop）.md)的决策。

如果没有软件工厂，每一次会话的开启都离不开某个人亲手去点开始。哪怕是完全无人值守的任务，也得等一个人打开会话、把它指向对应的 [Ticket](./Ticket（任务单）.md)，然后按下启动键。团队想要交付的产出远远超出这种方式的上限。软件工厂把人类从“启动会话”这件事里解放出来，但未必把人类从其他所有环节都移出去。

常见触发器及其启动的会话：

| 触发器                 | 启动的会话类型     | 示例                                                                                 |
| ---------------------- | ------------------ | ------------------------------------------------------------------------------------ |
| Issue 创建或打上标签   | 探索、修 Bug、实现 | 一个被打上 `ready-for-agent` 标签的 Issue 会触发一个会话来自动提交 PR                |
| 定时任务（cron）       | 周期性维护         | 每晚自动修复一条 Lint 规则                                                           |
| CI 失败或监控告警      | 诊断、尝试修复     | 主干分支构建失败时触发会话，找出引入问题的提交并给出修复方案                         |
| 另一个会话结束         | 后续跟进工作       | 一个 Agent 提的 PR 触发[自动化审查](./自动化审查（Automated%20review）.md)，审查意见再触发修复会话 |

软件工厂并不需要覆盖整个软件研发流程。哪怕只有一个定时任务，每晚跑一种会话并提一个可供审查的 PR，它就已经是一个软件工厂了。从小处着手非常有用：窄小的闭环产出的是一批规模小、结构相似的 PR，审查它们能让你清楚这个闭环在多大程度上值得信赖，然后再逐步扩大范围。

人类可以坐在软件工厂的任何环节上——编写并标记触发会话的 Issue、在实现开始前审批计划、在合并前做[人工审查](./人工审查（Human%20review）.md)。决定把哪些决策权保留给人类，是设计软件工厂的核心问题。如果一个代码库或其部分模块里，没有任何人类审查工厂的产出，那就是[黑灯工厂](./黑灯工厂（Dark%20factory）.md)。

_用法示例：_

“那些 `no-floating-promises` 的报错是谁全修掉的？”

“软件工厂干的。定时任务每晚挑一条 Lint 规则去修，然后提个 PR。我早上起来审查一下就行。”
