[模型提供商](./模型提供商（Model%20provider）.md)侧的存储机制，使连续的[模型提供商请求](./模型提供商请求（Model%20provider%20request）.md)可以跳过对共享前缀的重复处理。当某次请求的开头部分与近期某次请求的开头完全一致——相同的 [System prompt](./System%20prompt（系统提示词）.md)、截至某一点为止相同的历史记录——提供商就会复用之前算好的结果，并将这部分 [Token](./Token（词元）.md) 作为[缓存 Token](./缓存%20Token（Cache%20tokens）.md)，按低得多的费率计费。

缓存之所以划算，是因为会话是只增不减（append-only）地增长的。每次请求都会把整个历史作为[输入 Token](./输入%20Token（Input%20tokens）.md) 重新发送（原因见该词条），而在正常的[会话](./会话（Session）.md)中，历史记录只会在末尾发生变化——每次请求都是前一次请求加上几条新消息。提供商只需处理一次那段很长的共享开头，把结果存下来，然后直接从前缀结束的位置继续计算。如果没有缓存，一个 50 个[轮次](./轮次（Turn）.md)的会话就得为第一轮的内容重复付费处理五十次。

缓存也会过期。一条缓存记录能保持“预热”状态多久因模型提供商而异——通常是几分钟，而不是几小时。如果让会话闲置超过这个时间窗口，下一次请求就会按全价重新构建一次前缀，之后缓存才会恢复生效。这主要是 [Harness](./Harness（驾驭框架）.md) 开发者需要操心的问题；作为用户，你能感知到的现象是：长时间停顿之后的请求会比停顿之前的请求更贵。

_用法示例：_

“为什么会话进行到一半，账单突然飙升了？”

“Harness 开始在每个轮次往 System prompt 里注入当前时间了。前缀缓存会在第一个发生变化的 Token 处失效，所以那之后的每次请求都按全价计费了。”
