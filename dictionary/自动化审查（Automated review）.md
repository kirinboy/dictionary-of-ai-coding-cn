由一个 [Agent](./Agent（智能体）.md) 审查另一个 Agent 的工作，通常会使用不同的[模型](./模型（Model）.md)或 [System prompt](./System%20prompt（系统提示词）.md)。它具有非确定性：会形成主观判断。它可以在任何环节运行——合并前的 PR 上、事后针对提交历史，或者在会话中途作为 [Subagent](./Subagent（子智能体）.md) 运行。CI 中的 LLM-as-judge 属于自动化审查，而不属于[自动化检查](./自动化检查（Automated%20check）.md)；决定分类的是断言_在做什么_，而不是它在哪里运行。

与工作 Agent 相互隔离，是它之所以有效的关键。让写了代码的那个 Agent 自己审查自己的工作，收效甚微——产生 Bug 的那个[会话](./会话（Session）.md)里也包含着导致这个 Bug 的推理过程，Agent 读到自己写下的结论时往往只会顺着确认一遍。而拥有全新[上下文窗口](./上下文窗口（Context%20window）.md)的审查者没有这种先入为主的包袱：它会像陌生人一样审视这份 diff，这正是代码审查所需要的视角。换用不同的模型或专门用于审查的 System prompt 会进一步放大这种优势——不同的模型有不同的盲区，而专门的 System prompt 可以把注意力精准聚焦在你真正关心的维度（安全、API 契约、性能），而不是泛泛地“找找问题”。

它位于其他审查层之间。自动化检查是确定性的，负责捕获可用机械规则断言的问题；[人工审查](./人工审查（Human%20review）.md)成本高昂，最难扩展。自动化审查正好填补中间地带：以机器的成本去捕获需要判断力的问题——比如误导性的函数命名、遗漏的边界条件。由于它是非确定性的，它既可能漏报也可能误报；请把它当作在人工介入之前抬高底线的过滤器，而不是取代人工的把关闸门。

_避免使用：_ “AI 审查（AI review）” / “Agent 审查（agent review）”——太含糊，无法区分这究竟是不是工作 Agent 自己在自查。

_用法示例：_

“从[无人值守（AFK）](./无人值守（AFK）.md)运行里出来的烂 PR 太多了。”

“在合并前加一步自动化审查——换个模型，配个独立的 System prompt，专门盯紧安全性和接口契约变更。”
