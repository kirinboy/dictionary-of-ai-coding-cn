[模型](./模型（Model）.md)输出看似自信实则错误的内容。可分为两种类型，各自成因与修复方式不同：

| 类型 | 出错表现 | 原因 | 解决办法 |
| ---- | -------- | ---- | -------- |
| _事实性（Factuality）_ | 捏造或弄错关于客观世界的事实——不存在的函数、错误的 API 签名、虚假的引用 | [参数知识](./参数知识（Parametric%20knowledge）.md)存在缺口，通常因为超出了[知识截止日期](./知识截止日期（Knowledge%20cutoff）.md) | 加载正确的[上下文知识](./上下文知识（Contextual%20knowledge）.md) |
| _忠实度（Faithfulness）_ | 输出偏离了已加载的上下文知识、用户指令或模型此前的推理 | [注意力退化](./注意力退化（Attention%20degradation）.md)；进入[愚钝区](./聪明区（Smart%20zone）.md)后会加剧 | [清空会话](./清空会话（Clearing）.md)或进行[上下文压缩](./上下文压缩（Compaction）.md) |

无论背后的事实是否真实，[下一个 Token 预测](./下一个%20Token%20预测（Next-token%20prediction）.md)都能生成流畅的输出——模型内部并没有“我不知道这件事”的信号，因此捏造出来的方法也会以与正确答案同样笃定的口吻呈现。产生幻觉的代码在构造上看似合理：如果那个 API 存在，它_大概_就会长那样。这正是它能躲过粗略审查、直到实际运行时才暴露报错的原因。

你必须分清自己面对的是哪种类型，因为其中一种的解决办法会让另一种雪上加霜。事实性问题意味着缺少知识：解决办法是补充上下文——文档、类型定义、源码文件。忠实度问题意味着知识就在那里，但在注意力竞争中落败了：解决办法是精简上下文。如果把忠实度问题误诊为事实性问题，你就会粘贴更多文档进去，结果上下文进一步膨胀，偏离变得更严重。当 Agent 弄错某件事时，先检查正确信息是否已经在上下文中，再判断属于哪种问题。

_避免使用：_ 把“幻觉”简单当作“错了”的同义词——如果不指明具体类型，这个词就没有诊断价值。

_用法示例：_

“它凭空捏造了一个 schema 上的 `parseAsync` 方法。”

“事实性幻觉还是忠实度幻觉？”

“我粘贴的文档里明明有这个方法——只是过了第 40 [轮次](./轮次（Turn）.md)后，它就不看那些文档了。”

“那就是忠实度问题。做一次上下文压缩再重新加载，别再往里塞更多文档了。”
