运行已训练好的[模型](./模型（Model）.md)以生成输出——这就是每次[模型提供商请求](./模型提供商请求（Model%20provider%20request）.md)时发生的事。[参数](./参数（Parameters）.md)保持固定不变；模型只是基于它收到的[上下文](./上下文（Context）.md)执行[下一个 Token 预测](./下一个%20Token%20预测（Next-token%20prediction）.md)。相对于[训练](./训练（Training）.md)而言，推理单次成本较低，但按 [Token](./Token（词元）.md) 计费，是使用模型的主要开销所在。

模型的生命周期分为两个阶段：

| 阶段 | 发生时机               | 具体做什么                                 | 参数状态 |
| ---- | ---------------------- | ------------------------------------------ | -------- |
| 训练 | 发布前，一次性完成     | 基于训练语料库生成参数                     | 写入中   |
| 推理 | 每次有人使用模型时发生 | 在你的上下文上运行冻结的参数以生成 Token   | 只读     |

你在推理阶段所做的任何操作都不会写回参数——这就是为什么你今天纠正过它的错误，明天却依然会重演。在下一个[会话](./会话（Session）.md)中，即便你之前仔细解释过修法，模型还是犯了同样的错，这并不是它无视了你，而是它根本没有能力从对话中学习。模型是[无状态](./无状态（Stateless）.md)的——连续性必须由外部来提供，也就是来自[上下文窗口](./上下文窗口（Context%20window）.md)或[记忆系统](./记忆系统（Memory%20system）.md)。

这一机制也解释了账单是如何产生的。每次请求都会让模型遍历整个上下文，因此费用随[输入 Token](./输入%20Token（Input%20tokens）.md)和[输出 Token](./输出%20Token（Output%20tokens）.md)的规模增长，而一个执行了数十次[工具](./工具（Tool）.md)调用的 Agent，会在每一次往返中为推理付费。这就是为什么上下文大小不仅是一个质量问题，也是一个成本问题。

_用法示例：_

“为什么费用是按用量阶梯计费，而不是买断制的固定授权？”

“你是在为推理付费——每次模型提供商请求都在提供商的硬件上运行模型。训练早已完成，但推理成本按请求持续产生，而一个[轮次](./轮次（Turn）.md)在调用工具时会展开成许多次请求。”
