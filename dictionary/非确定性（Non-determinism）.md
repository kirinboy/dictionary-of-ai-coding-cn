相同的输入可能产生不同的输出。用完全相同的[上下文](./上下文（Context）.md)把[模型](./模型（Model）.md)跑两遍，你可能会得到两个不同的回答——有时只是差一个词，有时则是截然不同的实现方案。你的代码不需要做任何改动，这种情况就会发生。

这是模型生成文本的方式以及[模型提供商](./模型提供商（Model%20provider）.md)处理[请求](./模型提供商请求（Model%20provider%20request）.md)的方式所决定的固有属性。在[推理](./推理（Inference）.md)期间，模型会生成一个覆盖所有可能下一个 [Token](./Token（词元）.md) 的概率分布，并从中采样一个——而且通常是有意带有一定随机性的，因为总是挑选概率最高的 Token 会导致文本重复且质量下降。只要在回答早期采样出了一个不同的 Token，后面所有的 Token 都会随之改变，一个不同的词就这样演变成了完全不同的解题思路。提供商侧的服务架构还会在此之上引入更多变数：请求会在共享硬件上被打包批处理，不同批次之间微小的浮点计算差异，就足以改变两个相近 Token 之间的胜负。没有任何开关能彻底消除这种现象。

因此，要预期一个 [Agent](./Agent（智能体）.md) 在同一项任务上的结果会存在波动范围。大多数回答会落在合理的质量钟形曲线内——这也是非确定性之所以可以接受的原因——但长尾现象真实存在：有些时候模型显得敏锐犀利，有些时候却像丢了魂。同一项任务，不同的掷骰子结果。这带来了两个实际影响。首先，重试是一种合理的策略：一次失败的尝试只是分布中的一次抽样，对同一任务发起一次全新的尝试，可能恰巧就会落在一个更好的结果上。其次，验证比使用确定性工具时更加重要——你不能只测试一次 Agent 的行为就指望它次次复现，必须由[自动化检查](./自动化检查（Automated%20check）.md)来兜底拦截那些抽样不佳的结果。

注意不要对这种现象过度脑补叙事。人类是天然的模式匹配机器，连续几次糟糕的运行很容易让人觉得“这周模型变笨了”。通常情况下，那只是概率分布使然。

_用法示例：_

“Claude 今天糟糕透了。他们是不是上线了一个更差的版本？”

“多半不是——模型输出本来就是非确定性的。同一项任务有好时候也有坏时候，先别急着找原因，明天再试一次看看。”
