**Model Context Protocol（模型上下文协议）。** 一种将外部工具服务器接入 [Harness](./Harness（驾驭框架）.md) 的协议——让 [Agent](./Agent（智能体）.md) 获得 Harness 内置[工具](./工具（Tool）.md)之外的更多工具能力。Agent 从来不会去“调用 MCP”；它调用的是一个工具，而这个工具恰好是 Harness 从某个 MCP 服务器获取的。该协议也暴露资源（只读数据）和提示词（可复用模板），但提供工具是其最主要的用途。

这一协议解决的是集成问题。如果没有统一标准，每个 Harness 都必须自己编写并维护一套 Linear 集成、一套 Slack 集成、一套数据库集成。有了 MCP，集成只需作为一个服务器编写一次，任何兼容 MCP 的 Harness 都可以使用它。Harness 连接到该服务器，服务器声明自己提供哪些工具，这些工具随即就能与内置工具一起供 Agent 调用。

其代价体现在[上下文](./上下文（Context）.md)上。服务器声明的每一个工具都会以定义的形式传给[模型](./模型（Model）.md)——包含名称、描述和参数 Schema——因为模型只能调用它知道的工具。最朴素的做法是在一开始就把所有定义全部加载进[上下文窗口](./上下文窗口（Context%20window）.md)：只要装上几个工具数量较多的服务器，[会话](./会话（Session）.md)还没等你打字，就已经被几千个 [Token](./Token（词元）.md) 的工具 Schema 占用了开局空间，把[注意力预算](./注意力预算（Attention%20budget）.md)消耗在当前任务根本用不上的工具上。

如今许多 Harness 通过工具搜索（tool search）来缓解这个问题：上下文中不再放完整的工具定义，而是只保留指向可用工具的[上下文指针](./上下文指针（Context%20pointer）.md)——Agent 按名称或用途搜索工具，仅在真正需要时才加载其定义。如果你使用的 Harness 还没有这个机制，上述初始开销依然存在，因此只启用当前项目真正需要的服务器是值得的。

_用法示例：_

“Agent 需要从 Linear 读取 Ticket。”

“在 Harness 里配置 Linear 的 MCP 服务器——它会把 Linear API 暴露成 Agent 可以调用的工具，省得你自己写定制的工具封装。”
