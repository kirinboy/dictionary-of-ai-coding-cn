从 [Harness](./Harness（驾驭框架）.md) 到[模型提供商](./模型提供商（Model%20provider）.md)的一次网络往返。Harness 发送当前的[上下文](./上下文（Context）.md)；提供商返回一次响应（要么是一次[工具调用](./工具调用（Tool%20call）.md)，要么是最终回答）。如果 [Agent](./Agent（智能体）.md) 调用了[工具](./工具（Tool）.md)，一条用户消息就可能衍生出许多次模型提供商请求——每一次[工具返回结果](./工具返回结果（Tool%20result）.md)都会触发下一次请求。

每次请求都携带全部内容：[System prompt](./System%20prompt（系统提示词）.md)、截至目前的完整对话、以及每一条工具返回结果。[模型](./模型（Model）.md)是[无状态](./无状态（Stateless）.md)的，提供商在请求之间不会保留任何状态——第 40 次请求会把第 39 次请求发过的内容原封不动再发一遍，外加新的一条工具返回结果。[前缀缓存](./前缀缓存（Prefix%20cache）.md)的存在，正是为了让这种重复发送在成本上变得可承受。

请求也是计费的基本单位。[输入 Token](./输入%20Token（Input%20tokens）.md)、[输出 Token](./输出%20Token（Output%20tokens）.md) 和缓存折扣均按次统计，这也是为什么一个看似无害的问题可能会花掉惊人的费用：成本并不与你输入的那句话成正比，而是与“请求次数 × 每次请求携带的上下文大小”成正比。

很有必要把“请求”和[轮次](./轮次（Turn）.md)区分开来。一个轮次是你与它的一次对话交互，而一个轮次——比如“修复这个失败的测试”——实际上会展开成一连串请求：

| 请求 | 模型返回                     | Harness 随后执行                 |
| ---- | ---------------------------- | -------------------------------- |
| 1    | 工具调用：运行测试           | 执行测试，追加失败输出           |
| 2    | 工具调用：读取测试文件       | 追加文件内容                     |
| 3    | 工具调用：读取源文件         | 追加文件内容                     |
| 4    | 工具调用：编辑源文件         | 应用修改，追加修改结果           |
| 5    | 工具调用：再次运行测试       | 执行测试，追加通过输出           |
| 6    | 最终回答：“已修复，测试通过” | 展示给你                         |

一个轮次消耗了六次请求——而且每一次都重新发送了整个上下文。当你纳闷 [Token](./Token（词元）.md) 都去哪儿了时，去数请求次数，而不是数轮次。

_用法示例：_

“就问了一个问题，怎么烧掉了四万个 Token？”

“看看工具调用吧——十二次 grep、八次 read、四次编辑。每次工具返回结果都会触发一次新的模型提供商请求，而且整个[会话](./会话（Session）.md)前缀每次都要重发一遍。”
