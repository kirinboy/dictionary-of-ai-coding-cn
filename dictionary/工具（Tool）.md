[Harness](./Harness（驾驭框架）.md) 暴露给 [Agent](./Agent（智能体）.md) 调用的函数——如 Read、Write、Bash、Search。工具是 Agent 感知和作用于[环境](./环境（Environment）.md)的方式：除了通过[工具返回结果](./工具返回结果（Tool%20result）.md)，它无法看到环境；除了通过[工具调用](./工具调用（Tool%20call）.md)，它也无法改变环境。每次工具调用都会产生一次额外的[模型提供商请求](./模型提供商请求（Model%20provider%20request）.md)，因为结果必须传回模型，模型才能决定下一步该做什么。

大多数编程 Agent 内置的工具：

| 工具   | 作用                                                 |
| ------ | ---------------------------------------------------- |
| Read   | 将文件内容作为工具返回结果返回                       |
| Write  | 在[文件系统](./文件系统（Filesystem）.md)中创建或编辑文件        |
| Bash   | 运行 Shell 命令并返回其输出                          |
| Search | 在整个代码库中查找匹配特定模式的文件或文本           |

一个工具由三部分定义：名称、功能描述以及参数 Schema。Harness 会在每次请求时将这些定义发送给[模型](./模型（Model）.md)，而模型选择工具的方式与它生成其他内容的方式完全相同——通过输出 [Token](./Token（词元）.md)，只不过在这里是一段带参数的结构化调用。模型本身从不执行任何操作；是由 Harness 读取该调用、运行对应的函数，再把结果传回。

工具列表决定了 Agent 的能力边界。一个能力很强的模型如果只配了狭窄的工具集，也只能成为一个受限的 Agent：它会把所有需求都硬塞进手头仅有的工具里，这也是为什么 Agent 如此重度依赖 Bash——Shell 是一个几乎能触及系统各处的万能工具。要干净利落地赋予 Agent 某项能力，就应该为它添加专门的工具；[MCP（模型上下文协议）](./MCP（模型上下文协议）.md)正是从 Harness 外部接入工具的标准协议。

工具定义在每次请求中都会占用[上下文](./上下文（Context）.md)，因此庞大的工具集在任何工具被调用之前就已经带来了固定开销——而且大量描述相似的工具还会降低模型选对工具的准确率。

_用法示例：_

“Agent 能直接查询预发布（staging）数据库吗？”

“往 Harness 里加一个只读权限的预发布库 `psql` 工具。没有对应工具的话，Agent 对文件系统之外的任何东西都是盲区。”
