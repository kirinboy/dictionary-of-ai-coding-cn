一种在运行时塑造 [Agent](./Agent（智能体）.md) 工作方式的预设——它将[权限模式](./权限模式（Permission%20mode）.md)与注入到 [System prompt](./System%20prompt（系统提示词）.md) 中的行为指令捆绑在一起。例如：对高风险调用进行提示的默认模式、禁止编辑并引导 Agent 进行调研的 **plan mode**、自动批准文件编辑的 **accept-edits** 模式，以及自动批准一切操作的 **bypass permissions** 模式（俗称 **YOLO mode**）。可在[会话中途](./会话（Session）.md)随时切换。

这种捆绑正是 Agent 模式区别于单纯权限设置的地方。权限模式只是一道闸门：它决定哪些[工具调用](./工具调用（Tool%20call）.md)可以通过。只有闸门的话，Agent 依然想改代码但改不了——它会提出写入请求、被拦截，然后再换别的方式尝试。而注入的行为指令消除了这种“想改的冲动”：plan mode 不仅仅是阻止编辑，它还告诉 Agent 当前正处于规划阶段，因此 Agent 会主动去阅读、提问并提出方案，而不是一味地顶着闸门硬撞。门控与引导指向了同一个方向。

在实践中，你会随着任务推进过程中信任度的变化而切换模式。同一个任务可以依次经过几种模式：方案还在酝酿时用 plan mode，最初几处精细修改用需要提示的默认模式，一旦 Agent 证明它理解了改动意图就切到 accept-edits，而在[沙箱](./沙箱（Sandbox）.md)内执行[无人值守（AFK）](./无人值守（AFK）.md)任务时则切到 bypass 模式。切换模式没有任何成本：对话会在原地继续，只是换上了新的权限和新的指令。如果你发现自己看都不看就一路批准每次提示，说明模式设得比你实际的信任度更紧；如果你一直在拒绝编辑操作，则说明设得太松了。

_厂商术语：_ Claude Code 称之为“permission modes（权限模式）”，Codex 称之为“approval modes（审批模式）”——这两个叫法都早于“行为指令捆绑”这一做法出现。

_用法示例：_

“我只是想让它出个方案，结果它一直在改文件。”

“切到 plan mode——它会阻止写入操作，让 Agent 专心待在调研阶段。”

“那待会儿的无人值守运行怎么办？”

“用 bypass mode，但只能在沙箱里面用。”
