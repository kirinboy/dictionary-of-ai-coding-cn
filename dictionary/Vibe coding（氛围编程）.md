一种工作模式：用户不经[人工审查](./人工审查（Human%20review）.md)就直接接受 [Agent](./Agent（智能体）.md) 的代码。diff 被视为不透明的黑盒——人们只关心程序运行起来的表现是否符合预期，而不关心里面是怎么写的。在这个过程中，[自动化审查](./自动化审查（Automated%20review）.md)和[自动化检查](./自动化检查（Automated%20check）.md)依然可能运行；Vibe coding 这个概念本身并不限定是否使用它们。

这个词源自 Andrej Karpathy，他在 [2025 年初提出这一说法](https://x.com/karpathy/status/1886192184808149383)：你“完全顺从感觉（fully give in to the vibes）”，并且“忘掉代码的存在”——描述你想要什么，全盘接受返回的结果，然后直接运行它来评判好坏。

Vibe coding 是用审查深度换取速度。在 Agent 驱动的开发中，阅读 diff 往往是最耗时的一步，跳过它就移除了主要瓶颈。对于试错成本很低的代码——[原型](./原型构建（Prototyping）.md)、一次性脚本、内部小工具——这是一个合理的权衡。但风险会随着代码生命周期的延长和重要程度的提升而放大。

代价会在日后显现。通过 Vibe coding 产生的改动不断累积，最终形成一个没人读过的代码库；由于当初只检查了外在行为，任何没有在表面行为中暴露的问题——比如把密钥写进了日志、遗漏的边界情况、或者悄无声息出错的数据处理逻辑——都会在无人察觉的情况下上线。直到某天系统出故障需要排查时，才第一次有人真正去读这些代码。当人工审查缺席时，任何仍在运行的自动化验证——测试、类型检查、自动化审查——就成了代码上线前的唯一闸门。把同样的态度套用到整个代码库（或其中一部分），且所有改动都来自[软件工厂](./软件工厂（Software%20factory）.md)时，这就是[黑灯工厂](./黑灯工厂（Dark%20factory）.md)。

_避免使用：_ 把“Vibe coding”当成“低质量 AI 编程”的同义词——这个词指代的是审查立场，而不是代码本身的质量。

_用法示例：_

“它在鉴权流程里改了什么，你看过吗？”

“直接 Vibe coding 的——登录还能正常用，我就只测了那个。”

“推送之前还是看一眼 diff 吧，在鉴权逻辑上只靠 Vibe coding，密钥就是这么漏进日志里的。”
