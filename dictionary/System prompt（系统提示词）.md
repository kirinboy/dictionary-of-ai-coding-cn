[Harness](./Harness（驾驭框架）.md) 在每次[模型提供商请求](./模型提供商请求（Model%20provider%20request）.md)开头附加的指令——即 [Agent](./Agent（智能体）.md) 的常驻行动简报：它是什么角色、该如何行事、可以调用哪些[工具](./工具（Tool）.md)、需要遵守哪些规范。通常在单个[会话](./会话（Session）.md)期间保持稳定。

System prompt 由 Harness 厂商编写，而不是由你编写。在编程类 Harness 中，它往往非常庞大——通常包含数万个 [Token](./Token（词元）.md) 的行为准则、工具说明和边界情况处理，并且每个[轮次](./轮次（Turn）.md)都会作为[输入 Token](./输入%20Token（Input%20tokens）.md) 计费。你自己的常驻指令也会一并附带其中：像 [AGENTS.md](./AGENTS.md.md) 这样的文件会在会话开始时紧邻 System prompt 加载，因此[模型](./模型（Model）.md)在看到你的消息之前，就已经把厂商的指令和你的指令放在一起读完了。

由于它在每次请求中都完全一致，因此构成了[前缀缓存](./前缀缓存（Prefix%20cache）.md)的起始部分——这也是 Harness 在整个会话期间将其固定不变、而不是边跑边改的原因之一。

模型在训练时就被设定为优先服从 System prompt，其次才是用户消息。因此，当 Agent 执意采用某种你从未要求过的规范，或者固执地按某种你改不掉的格式输出时，它通常是在服从自己的 System prompt——而你的消息在优先级竞争中落了下风。部分 Harness 是可定制的：它们向你开放 System prompt 的完整访问权限，让你可以查看 Agent 到底收到了什么指令，并按需修改。

_用法示例：_

“两个 Harness，用着同一个模型，同一条提示词跑出来的行为却完全不同。”

“System prompt 不一样。一个调教成只做简短代码修改，另一个偏重讲解说明——在你的消息还没送达之前，差异就已经决定了。”
