---
description: 两个 Token 之间的配对关联——有意义的配对彼此影响更大，无关的则微弱。长度为 N 个 Token 的上下文大约有 N² 对这样的关联。
---

在预测每一个 [Token](./Token（词元）.md) 时，[模型](./模型（Model）.md)都会把[上下文](./上下文（Context）.md)里的其他所有 Token 纳入考量——有的权重很重，有的几乎忽略。两个 Token 之间的配对就是一种**注意力关联**，有意义的配对（比如“her”与“Sarah”，或一次 `getUser()` 调用与其 `function getUser` 定义）彼此之间的影响远大于无关配对。一个包含 N 个 Token 的上下文，大约有 N² 数量级的关联。

模型表面上呈现出的“理解力”，正存在于这些配对之中。当它正确解析一个代词时，是因为“her”和“Sarah”之间的注意力关联很强。当它用正确的参数调用一个函数时，起作用的是调用点与它前面读到的函数定义之间的关联。这些都不是查表得来的——而是在每次[模型提供商请求](./模型提供商请求（Model%20provider%20request）.md)中，针对每一对 Token 重新计算出来的。

N² 这个数字值得细想一下，因为它的增长速度远超直觉：

| 上下文规模 | 配对数量（约 N²） |
| ---------- | ---------------- |
| 1,000 个 Token | 约 100 万 |
| 10,000 个 Token | 约 1 亿 |
| 100,000 个 Token | 约 100 亿 |

而且每一对关联还不止计算一次。模型拥有多个注意力头（attention heads）——前沿模型的具体数量并未公开，但五十到一百个是合理的估计——每个头都会独立计算一遍每对关联的各自版本。因此上表中的每一对配对，都会在每个注意力头上重复计算一遍。这可是极其庞大的配对总量。

对于任何具体任务来说，这些关联里只有极少数真正重要。你的指令与它所约束的代码之间的配对，就是那寥寥几对关键关联之一；池子里其余绝大部分都是噪音。而且两者的增长速度截然不同：重要的关联数量基本保持不变，而整个配对池却随着上下文规模呈平方级膨胀。在 1,000 个 Token 时，你在意的配对是百万分之一；到了 100,000 个 Token 时，它就变成了百亿分之一。这就是[注意力预算](./注意力预算（Attention%20budget）.md)背后的算术逻辑，而当关键关联所占的份额被稀释得太薄时，表现出来的就是[注意力退化](./注意力退化（Attention%20degradation）.md)。

_用法示例：_

“它在 diff 里老是把那两个 `user` 符号搞混——听起来我们已经掉进[愚钝区](./聪明区（Smart%20zone）.md)了。”

“没错，每个调用点与其声明之间的注意力关联正在互相干扰——Token 形状相同，绑定却不同。把其中一个重命名，关联就会清晰起来。”
