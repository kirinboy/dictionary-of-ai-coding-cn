---

一种界定单个[会话](./会话（Session）.md)工作范围的[交接产物](./交接产物（Handoff%20artifact）.md)。它可以独立存在，也可以作为子项挂在某份 [Spec](./Spec（规格说明书）.md) 下。Ticket 可以阻塞兄弟 Ticket，也可以被它们阻塞，因此工作的执行顺序自然由它们的依赖关系图决定，而不是死板的线性计划。

最核心的约束在于粒度：一个会话。一个 Ticket 应当在会话滑出[聪明区](./聪明区（Smart%20zone）.md)之前就能完成——而且这个约束是可以检验的。如果你在执行 Ticket 时，会话经常还没做完工作就出现质量退化，说明 Ticket 太大了，需要拆分；如果每个会话把大部分[上下文](./上下文（Context）.md)都花在前期准备上，真正干活只花了五分钟，说明 Ticket 太小了，需要合并。

一份好的 Ticket 是为没有任何其他上下文的读者编写的。它应包含目标、验收标准，以及指向相关文件和决策的[上下文指针](./上下文指针（Context%20pointer）.md)——足以确保新会话一上来就能开工，而不用重新推导上一个会话已经知道的信息。

依赖关系图也是实现并行的关键。彼此独立的 Ticket——即依赖图中的叶节点——可以各自在独立会话中同时运行。这是同时运行多个 Agent 的有效方式。在[软件工厂](./软件工厂（Software%20factory）.md)中，一个 Ticket 被标记为就绪（ready），本身就是触发其会话启动的事件。

_用法示例：_

“迁移 Spec 该从哪里开始下手？”

“看 Ticket 依赖图——数据库结构变更阻塞了数据回填，数据回填又阻塞了 API 切换。挑一个叶节点，为它开一个会话吧。”
