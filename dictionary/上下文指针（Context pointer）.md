在一个文档中提及并指向另一个文档的线索，使 [Agent](./Agent（智能体）.md) 仅在任务需要时才将其拉入[上下文窗口](./上下文窗口（Context%20window）.md)。它是构成[渐进式披露](./渐进式披露（Progressive%20disclosure）.md)的基本单元。

使用指针（而不是直接内联内容）的原因在于成本。指针在上下文窗口中只占一行，它背后指向的文档可能有数千个 [Token](./Token（词元）.md)，但在 Agent 真正顺着指针去读之前，这些 Token 不会产生任何开销。把一份 2,000 Token 的运行手册内联进 [AGENTS.md](./AGENTS.md.md)，每次[会话](./会话（Session）.md)都要为它买单；如果换成“部署流程：见 `internal/deploy.md`”，就只有执行部署的会话才会加载它。当任务匹配时，Agent 会通过一次[工具调用](./工具调用（Tool%20call）.md)顺着指针去读取。

一个指针需要两个要素才能奏效：稳定的路径，以及足够清晰的描述，让 Agent 知道什么时候值得去读它。光给一个路径，Agent 就没有理由去跟进；只写“见 `internal/deploy.md`”而不提示里面有什么，真正需要它的会话往往会直接跳过。要把这行说明写成贴合任务出现方式的表达：“发布、部署或回滚前，请先阅读 `internal/deploy.md`”。

只要留意一下，指针其实无处不在：AGENTS.md 里的条目、[Skill](./Skill（技能）.md) 的描述（Harness 只加载描述，Skill 正文留在后面）、目录列表里的文件名、文档之间的链接，以及 [Home Repo](./Home%20Repo（主控仓库）.md) 的 AGENTS.md 里列出各个其他仓库的那几行。

指针还可以把[二手信源](./二手信源（Secondary%20source）.md)重新关联回它所衍生自的[一手信源](./一手信源（Primary%20source）.md)——比如标明原始对话记录的压缩摘要，或者标明所描述源码文件的文档。这让二手信源的信息损耗变得可恢复：当摘要不足以支撑判断时，Agent 可以顺着指针去读原始文件，而不必只依赖摘要里保留下来的内容。

_避免使用：_ “reference（引用）”——太干瘪，体现不出顺着它就能把更多上下文拉进来的意思；“portal（传送门）”——太花哨。

_用法示例：_

“AGENTS.md 变得越来越大了。”

“里面大部分都应该改成上下文指针，而不是直接放正文。只保留始终生效的规则；把部署手册和风格指南拆成 Skill，在原处留一个上下文指针就行。”
