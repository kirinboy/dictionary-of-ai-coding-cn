Agent 体验（Agent experience）——[环境](./环境（Environment）.md)为 [Agent](./Agent（智能体）.md) 在代码库中顺利开展工作所做的准备程度，是面向 Agent 的 [开发者体验（DX）](./开发者体验（DX）.md)。当同一个 Agent 在一个仓库里表现出色，在另一个仓库里却一塌糊涂——用的明明是同一个[模型](./模型（Model）.md)、同一个 [Harness](./Harness（驾驭框架）.md)——差距通常就出在 AX 上。人的第一反应往往是怪模型不行或者重写提示词；但真正的解法多半在代码库本身。

良好的 AX 主要包含三个维度：

| 维度       | 良好的 AX 应该是什么样                                                                                                                                      |
| ---------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 自动化检查 | 快速、确定性的[自动化检查](./自动化检查（Automated%20check）.md)——类型检查、测试、Lint——让 Agent 无需人类介入就能自我纠正                                                |
| 架构设计   | 让 Agent 无需通读全部代码就能定位导航的结构：可预测的目录组织、藏在精简接口之后的丰富行为、见名知意的命名                                                   |
| 可用上下文 | 将 [AGENTS.md](./AGENTS.md.md)、[Skill](./Skill（技能）.md) 和[工具](./工具（Tool）.md)保持精简，让大部分[上下文窗口](./上下文窗口（Context%20window）.md)留给当前任务，使 Agent 留在[聪明区](./聪明区（Smart%20zone）.md)而不是被信息淹没 |

AX 与 DX 存在交集——良好的检查和清晰的架构对人类和 Agent 都有益——但它们也会产生分歧。人类可以容忍口口相传的部落知识、缓慢的 CI，以及“计费模块的事去问 Sarah”；但 Agent 做不到。Agent 无法从 IDE 的悬停提示或漂亮的仪表盘中获益；它需要的是通过[工具返回结果](./工具返回结果（Tool%20result）.md)呈现的文本报错。一个代码库完全可能拥有极佳的 DX，同时却有着糟糕的 AX。

_避免使用：_ 把 AX 当作 DX 的同义词——这两类受众需要不同的投入。

_用法示例：_

“Agent 在 API 仓库里写的代码很棒，到了前端仓库就写出一堆垃圾。”

“API 仓库有严格的类型和快速的测试套件；前端仓库这两样都没有，还常驻加载了四十个 Skill。这是 AX 的差距，不是模型的问题。”
