[模型提供商](./模型提供商（Model%20provider）.md)从先前的[模型提供商请求](./模型提供商请求（Model%20provider%20request）.md)中缓存下来的[输入 Token](./输入%20Token（Input%20tokens）.md)，使其无需重复处理。当连续的请求共享同一段前缀时，提供商通过其[前缀缓存](./前缀缓存（Prefix%20cache）.md)复用计算结果，并对已缓存的部分按低得多的费率计费。这正是让长[会话](./会话（Session）.md)在费用上变得可承受的关键杠杆——没有它，每个[轮次](./轮次（Turn）.md)都得为全部历史重新付费。

之所以重要，是因为会话的计费方式决定的。[模型](./模型（Model）.md)是[无状态](./无状态（Stateless）.md)的，因此每次请求都会把整段对话——[System prompt](./System%20prompt（系统提示词）.md)、每一条消息、每一条[工具返回结果](./工具返回结果（Tool%20result）.md)——作为输入 Token 重新发送一遍。到了第 50 轮，每次请求都要携带 50 轮的历史记录，原本你每次都得为所有这些内容付全价。缓存改变了这笔账：对于提供商在完全一致的前缀中已经处理过的 Token，会按缓存 Token 计费，通常只有普通输入单价的十分之一甚至更低。在一个长会话中，你发送的大部分内容都是缓存 Token，账单因此得以保持在合理范围内。

下面这个例子展示了 Token 何时能命中缓存、何时不能。每个字母代表一块对话内容，每次请求发送截至目前的全部对话：

| 请求发送 | 命中缓存 | 按全价计费 | 原因                                   |
| -------- | -------- | ---------- | -------------------------------------- |
| `AB`     | 无       | `AB`       | 首次请求——没有可匹配的前缀             |
| `ABC`    | `AB`     | `C`        | `AB` 是前一次请求的精确前缀            |
| `ABCD`   | `ABC`    | `D`        | 前缀依然保持完整                       |
| `AXCD`   | `A`      | `XCD`      | 一处编辑把 `B` 改成了 `X`；匹配在此中断 |

这种缓存有一个特定的脆弱之处：它要求**精确前缀匹配**。只要对话靠前的部分有任何改动——[Harness](./Harness（驾驭框架）.md) 重新排列了内容顺序、更新了时间戳、改变了某个文件的表示形式——缓存就会从那个位置开始失效，之后的所有内容都会按全价输入计费。此外，缓存也会在几分钟无活动后过期，因此长时间暂停后恢复的会话会重新为历史记录付一次全价。当某个会话的费用无故暴涨时，在用量报告里对比一下缓存 Token 和输入 Token 的比例——缓存失效最先就会体现在这里。

_用法示例：_

“长会话的费用太吓人了——做一次重构花了我八美元。”

“查一下缓存 Token 吧。如果 Harness 在轮次之间重排了 System prompt 或文件的顺序，前缀就会断裂，导致你每次请求都在按全价付输入费。”
